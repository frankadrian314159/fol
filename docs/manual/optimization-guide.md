# FOL Compiler Optimization Guide

This guide covers compiler-level optimizations available in FOL to improve performance. These optimizations are automatically applied during compilation with zero runtime overhead.

## Overview

FOL implements three phases of optimization:
- **Phases 1-2**: Persistent object field access optimization (2-29% improvement)
- **Priority 2**: Type-aware dispatch and collection operations (2.6× on AST-heavy workloads)
- **Type Annotations**: Compile-time type hints for SBCL optimization (zero cost)

## Phase 1-2: Direct Slot Access Optimization

### What It Does

FOL's persistent objects use field accessors via the collection protocol. Phases 1-2 replace expensive generic dispatch with direct Common Lisp `slot-value` access.

**Before** (generic dispatch):
```lisp
(get obj :field)  ;; ~500-800ns per access
```

**After** (direct slot access):
```lisp
(cl:slot-value obj 'field)  ;; ~10-20ns per access
```

### How It Works

1. **Phase 1**: Accessor functions generated by `defclass` emit direct `slot-value`
2. **Phase 2**: Inline getter patterns detected and optimized with a global type registry

### Performance Impact

| Workload | Improvement |
|----------|------------|
| Interpreter | 29% |
| DVI (Derived-Value Invalidation) | 13% |
| AST Optimizer | ~0% (dominates at different level) |
| Collection operations | 10-25% |

### When It Applies

Automatically applied to all persistent objects created with `defclass`. No user action needed.

**Triggers optimization:**
```lisp
(defclass <point> ()
  ((x :initarg :x)
   (y :initarg :y)))

;; Generated accessor uses direct slot-value:
(get (make-<point> :x 1 :y 2) :x)  ;; Fast!
```

## Priority 2: Type-Aware Collections & Predicate Fast-Path

### What It Does

When FOL can infer the type of a collection at compile time, it uses that information to:
- Emit specialized code paths for known types
- Avoid full predicate matching in multi-clause functions
- Use direct slot-value for fields of known types

**Effect**: 2.6× speedup on AST optimizer (264.6× → 101.3× slower than CL baseline)

### How It Works

1. **Type Extraction**: Compiler extracts type from pattern specializers (e.g., `({:keys [...]} <op-add>)`)
2. **Type Registry**: Maps type names to field slots at compile time
3. **Optimization**: Substitutes generic `get` with direct `slot-value` for known types

### Example

```lisp
(defmethod optimize-expr
  [({:keys [(left ({:keys [(val (eql 0))]} <op-lit>))] } <op-add>)]
  ;; Type <op-add> is known here, so nested field access uses slot-value
  (simplify-to-right-operand ...))
```

### When It Applies

Automatically applied in multi-clause methods and functions with type specializers.

**No user configuration needed** — compiler detects patterns automatically.

### Performance Impact

| Scenario | Improvement |
|----------|------------|
| AST optimizer | 2.6× speedup |
| Pattern-heavy dispatch | 10-30× on pattern matching |
| Generic dispatch | No change (fallback available) |

## Type Annotations with Metadata

### What It Does

Use Clojure-style `^TYPE` syntax to add SBCL type hints that enable compile-time optimizations.

### Syntax

```lisp
;; Type annotation before function name
(defn ^cl:fixnum add [a b]
  (cl:+ a b))

;; Generates SBCL declaration:
(defun add (a b)
  (declare (ftype (function (t t) cl:fixnum) add))
  (cl:+ a b))
```

### How It Works

1. **Reader**: `^TypeName form` → `(with-meta form (dict :type TypeName))`
2. **Parser**: `parse-defn` extracts metadata from with-meta wrapper
3. **Emitter**: `emit-defn` generates SBCL `(declare (ftype ...))` forms
4. **SBCL**: Uses type information for optimization

### Examples

#### Basic Type Annotation

```lisp
;; Before
(defn factorial [n]
  (if (<= n 1) 1 (* n (factorial (dec n)))))

;; After - add type hint
(defn ^<fixnum> factorial [n]
  (if (<= n 1) 1 (* n (factorial (dec n)))))
```

#### Multiple Return Types

```lisp
;; Specify return type
(defn ^<double-float> compute-average [numbers]
  (/ (apply + numbers) (count numbers)))
```

#### Complex Function Types

```lisp
;; For functions with multiple dispatch, annotate each clause
(defn ^<number> process
  [^<fixnum> x]
  (+ x 1))  ; specialized for fixnum

(defn ^<number> process
  [^<double-float> x]
  (* x 2.0))  ; specialized for double
```

### Performance Impact

**Compile-time optimization only** — SBCL can:
- Inline type-checked code paths
- Eliminate type-check branches
- Use specialized machine operations
- Perform better register allocation

Expected improvements: 5-30% on heavily-typed code (depends on SBCL optimization level)

### Best Practices

1. **Add types to hot paths**: Functions called frequently
2. **Use precise types**: `cl:fixnum` not `cl:integer`
3. **Avoid overly-specific types**: `t` (any type) is fine for generic code
4. **Test with SBCL optimizations**:
   ```lisp
   ;; Tell SBCL to trust your types and optimize aggressively
   (declaim (optimize (safety 0) (speed 3)))
   ```

### Supported Type Specifiers

FOL's native type system (recommended):

**Numeric Types**:
- `<fixnum>` — Machine-word integer (30/60-bit signed)
- `<integer>` — Arbitrary-precision integer
- `<double-float>` — 64-bit IEEE floating point
- `<single-float>` — 32-bit IEEE floating point
- `<number>` — Generic numeric type (fixnum, float, ratio, complex)
- `<real>` — Real numbers (integer, float, ratio)
- `<complex>` — Complex numbers

**Collection Types**:
- `<vector>` — Persistent vector
- `<list>` — Linked list
- `<dict>` — Associative map
- `<set>` — Set collection
- `<string>` — String type

**Other Types**:
- `<symbol>` — Symbol
- `<keyword>` — Keyword
- `<boolean>` — Boolean (true/false)

### Using Common Lisp Types (Advanced)

If you need direct access to Common Lisp types for SBCL optimization:

- `cl:fixnum` — Maps to `<fixnum>`
- `cl:integer` — Maps to `<integer>`
- `cl:double` or `cl:double-float` — Maps to `<double-float>`
- `cl:single-float` — Maps to `<single-float>`
- `cl:vector` — Maps to `<vector>`

Most users should prefer FOL's type names, which are more portable and idiomatic.

## Optimization Levels

### Recommended Settings

**For Development** (safety first):
```lisp
(declaim (optimize (safety 2) (speed 1)))
;; Fewer optimizations, more runtime checks
;; Good for catching type errors early
```

**For Performance**:
```lisp
(declaim (optimize (safety 0) (speed 3)))
;; Maximum optimization, trust type annotations
;; Use when all types are correctly annotated
```

**Balanced** (recommended):
```lisp
(declaim (optimize (safety 1) (speed 2)))
;; Reasonable tradeoff
;; Good for most production code
```

## Interaction with Dispatch Caching

FOL includes dispatch caching for multi-clause functions. Type annotations work alongside caching:

1. **Dispatch caching** eliminates type-check overhead in hot paths
2. **Type annotations** enable SBCL to optimize the cached code

Combined effect: **7.5-20× speedup** on method dispatch (from caching alone)

Example:
```lisp
(defn ^cl:fixnum process
  ([^cl:fixnum x]
   (cl:+ x 1))
  ([^cl:double x]
   (cl:* x 2.0)))

;; Dispatch caching optimizes dispatch
;; Type annotations let SBCL optimize the chosen method body
```

## Troubleshooting

### Types Aren't Being Optimized

1. Check SBCL optimization settings: `(declaim (optimize (speed 3)))`
2. Verify types are correct: use Common Lisp type specifiers
3. Profile to see if that code path is actually hot
4. SBCL may choose not to optimize if unsure — very conservative

### Type Conflicts

```lisp
;; Wrong: conflicting return types
(defn process [x]
  (if condition
    (return-fixnum x)    ; returns cl:fixnum
    (return-vector x)))  ; returns vector — type mismatch!

;; Right: use union type or generic return
(defn process [x]
  (if condition
    (return-fixnum x)
    (return-vector x)))
  ;; Don't specify return type, let SBCL infer
```

### Performance Not Improving

1. **Wrong optimization level**: Set `(speed 3)` if you want aggressive optimization
2. **Non-hot code**: Type hints help most on frequently-called functions
3. **Type too generic**: `t` means "any type" — SBCL can't optimize
4. **SBCL can't inline**: Some functions are too large or complex for SBCL to optimize
