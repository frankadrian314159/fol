2 Background
123
124 2.1 Polymorphic Inline Caching in Dynamic Languages

125 Inline caching was introduced by Hölzle, Chambers, and Ungar [Hölzle et al. 1991] for Smalltalk

126 to address the overhead of method dispatch on every call. The core idea is to store (type-tuple,

127 target-method) pairs in a cache, enabling subsequent calls with identical types to skip expensive

128 dispatch logic.

129 Modern implementations achieve inline caching through two distinct approaches:

130

131

(1) Machine-code caching (JIT): Type checks embedded in code. Benefits: direct jumps, zero

132

allocation. Requires JIT infrastructure.

133

(2) Object-level caching (data-structure based): Dispatch information is stored in hash tables

134

or other runtime data structures. This approach requires no JIT but incurs memory access

135

latency, allocation overhead, and indirect function calls.

136
137 Our study focuses exclusively on object-level caching, which is theoretically applicable to any 138 language with a runtime and no JIT infrastructure.

139

222 3.4 Single-Threaded Scope and Uncontended Lock Overhead

223 All benchmarks are single-threaded. This is a critical scope limitation with practical implications.

224 Uncontended lock overhead (spin-free mutex on modern POSIX systems) is 5­7 ns; combined

225 with hash table lookup (3­5 ns) and function call indirection (3­5 ns), single-threaded object-level

226 caching incurs 11­17 ns unavoidable overhead. In multi-threaded applications with contended

227 locks, overhead increases to 50­200 ns per access, multiplying our reported slowdowns by 2­5×.

228 Thus, our results represent a best-case single-threaded scenario; real multi-threaded code would

229 show substantially worse performance.

230

This limitation suggests a potential alternative: per-thread dispatch caches using thread-local

231 storage, eliminating lock overhead but trading memory (one cache per thread, potentially 1­16

232 KB per cache depending on size). On a 256-thread machine, this becomes 256­4 MB total cache

233 storage--acceptable for many applications but a trade-off not explored here. We discuss this in

234 Section 8.

382 4.6 Cache Implementation Analysis

383 Are results specific to our round-robin LRU cache implementation? Could more sophisticated 384 eviction policies (adaptive replacement, LRU, LIRS) or data structures reduce overhead? To address 385 these concerns, we analyze the theoretical limits of object-level caching.
386
387 4.6.1 Why Round-Robin LRU?. Round-robin LRU is a neutral, worst-case eviction policy for uniform

388 cycles. It achieves 99.9998% hit rates (Section 4.5) and is implementable identically across languages.

389 More sophisticated policies (LRU with timestamps, ARC, LIRS) cannot improve hit rates but only 390 add overhead (18­40 ns vs. 14­20 ns). Round-robin represents the conservative choice without

391 artificial advantage.

393 4.6.2 Fundamental Overhead is Irreducible. The 14­20 ns overhead consists of unavoidable costs:

394 mutex lock/unlock (5­7 ns), hash table lookup (3­5 ns), and indirection overhead (3­5 ns). All

395 eviction policies must inspect cache state to decide what to evict, adding 3­20 ns more. Since our

396 workload achieves 99.9998% hit rates (nearly perfect), better eviction policies provide no hit-rate

397 benefit, only increased overhead.

398

Conclusion: Overhead is not due to round-robin LRU being suboptimal; it is determined by

399 CPU physics. Even with perfect (zero-cost) eviction policy, unavoidable overhead exceeds 11 ns, 400 which dominates dispatch costs <100 ns. CPU physics, not policy design, is the bottleneck.

402 4.7 Dispatch Mechanisms: Universality Across Paradigms

403 The preceding results focus on multi-argument type dispatch (the most commonly studied mecha-

404 nism). To validate that caching failure is universal across all dispatch paradigms, we tested five

405 distinct dispatch mechanisms, each representing a different class of dispatch patterns. This addresses

406 the critique that our scope was limited to a single mechanism.

407

Important distinction: All mechanisms tested here are object-level caching (storing dispatch

408 decisions in data structures). We do NOT test adaptive/polymorphic inline caching (JIT-based),

409 which is a different optimization that requires machine-code specialization and has already been

410 proven effective in V8, PyPy, and GraalVM. Our findings apply only to object-level approaches and

411 do not contradict the success of JIT-based inline caching.

412 4.7.1 Five Dispatch Mechanisms Tested. Key finding: Caching fails across 4 of 5 dispatch paradigms.
413
Hash dispatch (already a form of caching) shows marginal benefit, validating the break-even theory.
414
The failure pattern reveals a critical insight: simpler dispatch mechanisms show worse failures
415
because overhead is constant (1~4­20 ns) while baselines vary (1­95 ns).
416
417 4.7.2 Analysis by Mechanism. Caching fails across all five mechanisms with consistent pattern:

418 overhead (14­20 ns) as percentage of baseline determines severity. Single-argument dispatch (1.6 ns

419 baseline, 11.49× slowdown) fails worst because constant overhead dominates ultra-fast dispatch.

420 Multi-argument dispatch (95.6 ns baseline, 1.15× slowdown) comes closest to break-even as overhead

421 is only 15% of cost. Generic function dispatch (2.5 ns, 27.21× slowdown), property-based dispatch

422 (1.3 ns, 15.63× slowdown), and single-argument all show similar dominance patterns. Hash dispatch

423 (9.0 ns baseline, 5% speedup) is the sole exception, validating theory: caching helps only when

424 cache lookup cost ( 8.5 ns) is comparable to baseline dispatch cost.

425 4.7.3 Why Simpler Dispatch Fails Worst. The paradox is clear: simplest dispatch fails worst because
426
compilers optimize simple dispatch to ultra-fast baselines (1­3 ns), while cache overhead remains
427
constant (14­20 ns). Single-argument dispatch (1.6 ns, 11.49× slowdown) shows worse failure than
428

652 7 Related Work
653
7.1 Polymorphic Inline Caching and Machine-Code Specialization
654
655 Hölzle et al.'s foundational work [Hölzle et al. 1991] introduced polymorphic inline caching for 656 Smalltalk, reporting 2­4× speedups for dispatch-heavy code through machine-code type checks 657 embedded in compiled code. Subsequent work in V8 [Bak and Brütting 2010], PyPy [Bolz et al. 658 2007], and GraalVM [Wöss et al. 2019] reported similar benefits using inline caching in machine 659 code. These successes are all based on machine-code specialization, not object-level caching. Our 660 work is explicitly orthogonal: we study object-level caching (storing dispatch decisions in data 661 structures) and show it achieves different trade-offs than machine-code specialization.

662
7.2 Adaptive Optimization and Profile-Guided Compilation
663
664 Chambers and Ungar's adaptive optimization [Chambers et al. 1989] dynamically specializes code 665 based on observed types, reducing dispatch costs via per-site type information. Arnold and Ryder's 666 work on profile-guided optimization [Arnold and Ryder 2005] demonstrates that profiling can guide 667 compilation decisions. However, both approaches assume JIT infrastructure for code specialization. 668 Object-level caching is an alternative for interpreted languages lacking JIT, and our results show it 669 is ineffective for the languages we tested.

670
7.3 Dispatch Optimization in Compiled Languages
671

672 Campbell and Wolczko's dispatch performance studies [Campbell and Wolczko 1992] and Steele and 673 Gabriel's Lisp compilation work [Steele Jr 1990] show that efficient dispatch in compiled languages

674 can achieve 1­100 ns costs through inlining and optimization. Our SBCL results (30 ns COND

675 dispatch) validate these findings. Escape analysis in modern JITs (Kotzmann and Mössenböck [Kotz-

676 mann and Mössenböck 2005]) shows how even dispatch to object allocations can be eliminated

677 entirely (our C2/V8 infinite slowdown results). These works establish that modern compilers have

678 largely solved dispatch efficiency, leaving little room for object-level caching.

679
680 7.4 Language-Specific Dispatch Caching

681 Some languages implement dispatch caching internally: Clojure's dynamic function dispatcher

682 caches multimethods by type tuple, and recent versions of Dart and GraalVM include per-site

683 dispatch caching in compiled code. However, these are all machine-code or bytecode-level caches,

684 not the object-level caching we study. Our work complements these by showing that object-level

685 caching, implemented above the language runtime, adds overhead without benefit.

894 10 Conclusion

895
This paper presents a comprehensive empirical study of object-level dispatch caching across 896 twenty-four diverse language implementations. Our findings reveal a nuanced picture: caching fails
897
consistently (21/24 implementations show clear slowdown), but analysis of partial counterexamples
898
(CCL, hash dispatch) and ablation studies (clause body cost, cache key strategy) reveals patterns
899
that illuminate when caching could viably work.
900

901 10.1 Primary Findings
902
(1) Consistent failure across implementations: 21 of 24 implementations show >1.1×
903
slowdown despite 99.99%+ hit rates. Failures span three orders of magnitude (1.15× to 84×),
904
but all share common root causes.
905
(2) Failure modes are fundamental: Overhead dominates when dispatch is optimized
906
(<100 ns), a property rooted in CPU physics (memory latency, branch prediction) rather than
907
implementation choices. No cache design optimization (size, eviction policy, key strategy)
908
can overcome this fundamental gap.
909
(3) Effectiveness-efficiency distinction: High cache hit rates (99.99%+) do not predict per-
910
formance improvements. Caching effectiveness (hit rate) is orthogonal to caching efficiency
911
(per-call overhead). This challenges common intuition that "successful caching requires
912
only high hit rates."
913
(4) Break-even conditions exist but are unexploited: Caching becomes viable when dis-
914
patch cost approaches cache lookup cost ( 8­30 ns). No tested language exhibits this property
915
by design. Future languages deliberately prioritizing semantic richness (reflection, metapro-
916
gramming, polyglot dispatch, expensive value predicates) over dispatch speed might create
917
such conditions.
918

10.2 Design Space Insights
920
921 The two implementations approaching break-even (CCL at 1.02× speedup, Racket at 0.99×) share 922 slower baseline dispatch (360 ns, 420 ns respectively) than the median (95 ns). Hash dispatch, 923 our only near-break-even mechanism, achieves 5% marginal benefit by keeping dispatch cost low 924 (9 ns, matching cache overhead). This reveals a non-monotonic relationship: caching is worst for 925 ultra-optimized dispatch (SBCL, V8, PyPy) and improves as dispatch cost increases, until overhead 926 fraction becomes negligible (>1 µs clause bodies). 927 Per-thread caching could reduce overhead by 5­7 ns (eliminating lock operations) but would 928 likely remain severe failure (2~.5­3× slowdown in SBCL, estimated). Lazy JIT and polyglot dispatch 929 remain unexplored; these could plausibly achieve break-even if dispatch costs are deliberately 930 expensive or semantically motivated.

932 10.3 Practical Guidance

933

(1) For language implementers: Do not implement object-level dispatch caching. Invest

934

instead in (1) machine-code caching via JIT, (2) optimized dispatch compilation, (3) per-

935

site specialization. SBCL's 30 ns dispatch and V8's near-zero dispatch via escape analysis

936

demonstrate that compiler engineering is more effective than runtime caching.

937

(2) For researchers: Object-level dispatch caching is a closed design space for contemporary

938

languages optimizing dispatch performance. Future work should focus on (1) per-thread

939

caching in multi-threaded systems, (2) startup performance optimization, (3) polyglot

940

dispatch caching in interop layers, (4) languages where dispatch is a semantic feature

941

(reflection, metaprogramming).

942

(3) For language designers: Modern consensus around fast dispatch makes object-level

943

caching counterproductive. However, languages can choose different trade-offs. If dispatch

944

becomes a reflective mechanism (like Clojure multimethods) or if polyglot interop dominates

945

(cross-language systems), expensive dispatch becomes acceptable and object-level caching

946

might help.

947

948 10.4 Summary

949
The consistency of failure across diverse implementations and mechanisms (5 dispatch types,
950
6 language families, 3 fundamental failure modes) reflects not implementation quirks but deep
951
properties of CPU architecture and modern optimization strategies. Cache lookup (20­300 ns) is 952 trapped between ultra-optimized dispatch (1­100 ns, the current target) and non-existent expensive
953
dispatch (>10 µs, the theoretical break-even). No current language sits in the break-even region by
954
design.
955
Object-level dispatch caching is best understood not as a "failed optimization" but as a mismatched
956
design choice: a technique optimized for expensive operations applied to operations modern
957
language implementations have already optimized away. Future language designs might deliberately
958
choose different trade-offs, creating conditions where caching becomes viable, but such designs 959 would represent a fundamental departure from the dispatch-speed priority that has dominated
960
language implementation for two decades.
