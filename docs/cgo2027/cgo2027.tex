\begin{abstract}
Persistent-first languages give programmers immutable objects, but a record
rebuilt every loop iteration becomes a stream of short-lived heap
allocations; on our benchmarks this allocation and its garbage collection
dominate the loop's runtime, and the loop runs
90--250$\times$ slower than an equivalent native mutable-struct loop. Classic
\emph{scalar replacement of aggregates} (SRA) removes such allocation, but the
textbook formulation only fires when an object is created and dies inside one
lexical scope, and it presupposes a \emph{closed world} in which a class's
shape never changes. Neither assumption holds for the case that actually
drives allocation: a record threaded through a loop's back-edge, in a
language---like FOL, a persistent-first Lisp transpiled to Common Lisp---where
classes can be redefined \emph{while the optimized code is running} and there
is no JIT to fall back on for safe deoptimization. This paper's central
contribution is making aggregate scalar replacement sound under that
open world: \emph{aggregate scalar replacement} (ASR) unboxes a persistent-record
loop accumulator into one scalar variable per field, reaches across a
helper-call boundary via a one-level syntactic inliner, avoiding
whole-program analysis, and is emitted as a \emph{world-guarded}
dual path whose fast path a redefinition transparently invalidates. A single
classify-and-rewrite walk is aligned by construction---any accumulator use it
does not recognize aborts the rewrite rather than miscompiling it---so the
transformation is never unsound, only sometimes inapplicable. To our
knowledge this is the first treatment of loop-carried aggregate scalar
replacement that is safe in an open, JIT-less, untyped world. We evaluate it
on two axes and report both honestly. On fourteen allocation-bound
microbenchmarks the technique eliminates per-iteration allocation entirely for
an end-to-end 3.1$\times$--16.3$\times$ speedup with byte-identical results
and no cost when disabled. On real Clojure code, an incidence proxy
since FOL has no user base of its own, the target pattern is rare
(0.55\% of loop/reduce accumulator sites across 29 real projects)---but where
it occurs, the mechanism delivers: porting a widely used router library's
whole record-accumulator builder, unmodified in shape, yields a
4.58$\times$ speedup with 3.22$\times$ less allocation, and an independent
extension to schema-less accumulators recovers
1.72$\times$ speedup with 1.89$\times$ less allocation for the same
builder written the more idiomatic way, against a plain map rather than a
declared class. The residual distance to native, larger than the allocation
share, is generic scalar arithmetic, closed by a complementary
numeric-specialization pass.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Languages built on persistent data structures let programmers treat records as
immutable values: an ``update'' produces a new version that structurally shares
with the old one. This is pleasant, but it has a cost. When
a small record is updated inside a loop, every iteration allocates a fresh
heap object, and the previous version becomes garbage immediately. In
FOL~\cite{adrian2026fol-els}---a Lisp-1 dialect with CLOS-like persistent
objects, transpiled to Common Lisp---a loop rebuilding a persistent record runs \textbf{90--250$\times$}
slower than the same loop over a native mutable \texttt{defstruct}
(\S\ref{sec:eval}). Allocation and its garbage collection dominate that loop's
\emph{runtime}---and are what this paper removes---but they are not the largest
part of the gap to \emph{native}. As \S\ref{sec:eval} shows, generic arithmetic
is a larger factor. We attack allocation first: it
produces garbage-collection pauses (which matter for latency, not merely
throughput) and is the enabling step for arithmetic work, since the scalars
it exposes are what a later type-specialization pass annotates.

The canonical remedy in a static, closed-world setting is \emph{scalar
replacement of aggregates} (SRA): if a compiler can prove an object does not
escape, it need not allocate it at all; the object's fields live in
local variables, and field accesses become variable accesses. Modern
JITs realize a powerful form of this via \emph{partial escape
analysis} \cite{stadler2014partial}, building on a long line of escape analyses
for object-oriented languages \cite{choi1999escape,blanchet2003escape}.

Two obstacles keep the textbook formulation from helping the programs that hurt
most in FOL. First, the \emph{scope} problem: the simplest SRA
only fires when an object is created and dies inside a single lexical
scope---a \texttt{let} whose body consumes the object and returns something
else, the least interesting case; a good backend often stack-allocates
it. The objects that actually drive allocation are \emph{loop
accumulators}: a record read, rebuilt, and threaded through a
\texttt{recur} back-edge every iteration, often via a
small helper returning a fresh record. Second, the \emph{open-world}
problem: FOL classes can be redefined at run time, so an optimization baking in
a class's field layout must remain correct even if that shape changes
\emph{while the optimized code runs}---something closed-world SRA never
has to consider.

This paper presents \emph{aggregate scalar replacement} (ASR) for FOL: an
emit-time transformation that unboxes a persistent-record loop accumulator
into one scalar loop variable per field. The scope and open-world problems
above are not incidental difficulties---doing SRA-style
unboxing \emph{safely} when neither a lexical-scope guarantee nor a
closed-world class layout can be assumed is the technical problem this paper
solves; the speedups in \S\ref{sec:eval} are a consequence, not the
point. Figure~\ref{fig:overview} shows the target pattern and the
result. Our contributions are:

\begin{enumerate}
  \item \textbf{Loop-carried record unboxing.} A transformation that splits a
  record accumulator into per-field scalar loop variables: \texttt{(get p :x)}
  becomes a variable read, the constructor that feeds \texttt{recur} becomes its
  field value-expressions (the loop's arity grows to match), and a single
  object is re-materialized only if the bare accumulator is returned at the loop
  exit (\S\ref{sec:loop}).
  \item \textbf{Interprocedural reach by inlining.} An object-returning callee
  at the recur position---the common shape \texttt{(recur (update p) \ldots)}---is
  inlined so that its tail constructor becomes the reconstruction expression,
  giving interprocedural unboxing without a whole-program ownership analysis
  (\S\ref{sec:inline}).
  \item \textbf{Soundness under live redefinition.} The converted loop is
  emitted as a \emph{world-guarded} dual path keyed on the record's class name;
  redefining the class invalidates the region and the next call transparently
  takes the original, object-allocating loop (\S\ref{sec:world}).
  \item \textbf{Alignment by construction.} A single walk both classifies and
  rewrites; any accumulator use it does not recognize aborts the rewrite and
  yields the original loop unchanged. The transformation is therefore never
  wrong, only sometimes inapplicable---the safe default for a compiler pass
  enabled on untyped code (\S\ref{sec:align}).
  \item \textbf{Evaluation.} On fourteen allocation-bound benchmarks from five
  domains---physics, image processing, state estimation, audio DSP, and online
  statistics---spanning two- to four-field records, additive, multiplicative,
  conditional, and division-bearing updates, and two coupled multi-accumulator loops, our
  technique reduces per-iteration allocation to zero for an end-to-end
  3.1$\times$--16.3$\times$ speedup (dominated by one dispatch-bound benchmark,
  \S\ref{sec:eval}; the rest span 3.1$\times$--7.0$\times$), produces byte-identical results, and adds no
  cost when disabled or inapplicable. We also measure a native
  mutable-\texttt{defstruct} implementation of each benchmark as an upper bound,
  reporting how much of the gap ASR closes and what the residual is
  (\S\ref{sec:eval}).
  \item \textbf{An honest reality check.} Because FOL has no user base, we
  proxy the target pattern's real-world incidence with a corpus study of 29
  Clojure projects: it is rare (0.55\% of loop/reduce accumulator sites),
  suggestively---though not conclusively---because idiomatic code already
  hand-writes the scalarized form ASR would otherwise produce
  (\S\ref{sec:discussion}). Where the pattern occurs we do not simulate
  it: we port a widely used router library's whole record-accumulator
  builder unmodified, and again as its more idiomatic schema-less-dict
  form under an independent extension of the same mechanism, measuring
  both against baseline at the same rigor as \S\ref{sec:eval}
  (Table~\ref{tab:reitit}, \S\ref{sec:discussion}).
\end{enumerate}

To our knowledge---\S\ref{sec:related} makes the comparison
precise---this is the first treatment of loop-carried aggregate scalar
replacement safe in an open, JIT-less, untyped world.

Our microbenchmark evaluation is deliberately focused: the technique targets
one high-value pattern---the loop-carried record accumulator---instantiated
with different field counts, update shapes, and accumulator multiplicities.
This is why the corpus study and whole-program port matter as
much as the speedup numbers: together they let us report an honest
picture of when the transformation fires, how often that happens in code we
did not write to flatter it, and what it buys where it does
(\S\ref{sec:discussion}).

\section{Background}

\textbf{FOL in one column.} FOL is a Lisp-1 dialect transpiled to Common Lisp
(SBCL). Persistent records are declared with \texttt{defclass}; a class
\texttt{<t>} induces a constructor \texttt{make-<t>} and keyword field
accessors read with \texttt{(get obj :field)}. A global type registry records
each class's field set. \texttt{(loop [bindings] \ldots (recur
new-vals))} provides tail-recursive iteration, lowered to a
\texttt{block}/\texttt{tagbody} with a \texttt{psetq} updating all loop
variables before jumping to the head. Forms are transpiled one
at a time, in source order.

\textbf{Why the accumulator is the hard case.} In
Figure~\ref{fig:overview}, the allocation lives in two places neither
a scope-local SRA can touch. In \texttt{update-point}, the \texttt{make-<point>}
is the function's \emph{return value}---it escapes to the caller. In
\texttt{run-simulation}, \texttt{p} is a \emph{loop parameter}, not a
\texttt{let}-binding, passed whole into \texttt{update-point}. To
remove it, one must reason across the call boundary and the
loop back-edge simultaneously---precisely what aggregate scalar
replacement does.

\textbf{Relationship to transient conversion.} A companion line of work makes
persistent \emph{collection} accumulators (dicts, vectors, sets) update in place
by converting them to Clojure-style transients, guarded for soundness under
redefinition. Aggregate scalar replacement is the analogue for user-defined
\emph{records}: rather than mutate a boxed object in place, it eliminates the box
entirely. Both share the world-guard machinery of \S\ref{sec:world} and
compose in the same \texttt{emit-loop} entry point, but that machinery is
shared infrastructure, not a claim of this
paper---our contribution is the record transformation of \S\ref{sec:algo},
described in full only because the guard makes it sound.

\section{Aggregate Scalar Replacement}
\label{sec:algo}

The transformation runs at loop-emission time. Given a \texttt{loop} node, it
searches the bindings for a parameter whose initializer is a record constructor
\texttt{(make-<t> \ldots)} (or the EQL-specialized \texttt{(make '<t> \ldots)})
of a class known to the type registry, and attempts
to unbox it, either succeeding with a rewritten loop or leaving it untouched.

The single-accumulator transformation is applied repeatedly to a fixpoint to
handle loops with multiple record accumulators. The pass unboxes one candidate,
re-scans the rewritten loop for another, and repeats until none remain.
This correctly handles coupled accumulators (where one's
update reads another's fields) because each pass makes a new set of scalar
fields available for the next, and the parallel \texttt{psetq} semantics of
\texttt{recur} ensures all updates are based on the values from the start of the
iteration. We now describe the single-accumulator case.

\subsection{Candidates and fields}
\label{sec:cand}

A loop parameter \texttt{p} is a \emph{candidate} when (i) its initializer is a
constructor call \texttt{(make-<t> :k1 v1 \ldots)}, (ii) \texttt{<t>} is in the
type registry with a known field set $F = \{f_1,\ldots,f_m\}$, and (iii) the
constructor supplies exactly the fields in $F$. For each field $f_j$ we mint a
fresh scalar loop variable named \texttt{p\_}$f_j$ (e.g.\ \texttt{p\_x}). The
loop binding for \texttt{p} is replaced by $m$ bindings \texttt{p\_}$f_j$
initialized to the corresponding constructor argument $v_j$. All keys are
canonicalized so the constructor initarg, \texttt{get} key, and registry
storage key coincide.

\subsection{Loop-carried unboxing}
\label{sec:loop}

The body is rewritten by a single recursive walk parameterized by whether the
current node is in tail position and by a set of \emph{alias} names that denote
the accumulator (initially $\{\texttt{p}\}$; \S\ref{sec:inline} explains why it
is a set). The walk maps each accumulator use to one of a few recognized
shapes (Figure~\ref{fig:algo} gives it in full):

\begin{itemize}
  \item \textbf{Field read.} \texttt{(get p :}$f_j$\texttt{)} rewrites to a
  reference to \texttt{p\_}$f_j$; a read of a key not in $F$ aborts.
  \item \textbf{Reconstruction at the back-edge.} At the recur position, the
  argument in the accumulator's slot must \emph{reconstruct} the record: the
  walk expands it into the $m$ per-field value expressions and splices them
  into the recur argument list in field order, growing the loop's arity
  from $k$ to $k+m-1$. A bare accumulator here (unchanged pass-through)
  expands to the current field variables.
  \item \textbf{Re-box at exit.} A bare accumulator reference in tail
  position (the loop's result) is re-materialized as \texttt{(make-<t> :}$f_1$
  \texttt{p\_}$f_1$ \ldots\texttt{)}---one allocation, at most once per
  loop activation.
  \item \textbf{Anything else aborts.} A bare accumulator passed to an
  arbitrary call, stored in a literal, captured by a closure, or reaching an
  unhandled node type fails the whole attempt. Since the walk builds the
  rewritten body functionally and signals failure by a non-local exit, a
  failed attempt has no effect: the original loop is emitted.
\end{itemize}

\begin{figure*}[t]
\begin{lstlisting}[language={},basicstyle=\fontsize{8pt}{9pt}\selectfont\ttfamily,numbers=none,frame=single,columns=fullflexible,keepspaces=true,keywordstyle={}]
Rewrite(n, tail, A):        # A = accumulator alias names; may raise Fail
  match n:
    (get p k), p in A    -> if k in F: return VAR(p_k) else Fail
    (recur ... a ...)    -> replace slot arg a by Reconstruct(a, A),  # k -> k+m-1
                            other args via Rewrite(., false, A)
    p, p in A and tail   -> return (make-<T> :f1 VAR(p_f1)...:fm VAR(p_fm)) # re-box
    p, p in A            -> Fail                    # bare accumulator escapes
    (bind bs e)|(do e)   -> peel; rewrite inits (false) and body (tail); re-wrap
    _                    -> recurse; any surviving p in A -> Fail

Reconstruct(a, A):          # returns m per-field expressions, in field order
  a := Peel(a)                              # strip single-form bind/do wrappers
  match a:
    (make-<T> :f1 v1...:fm vm), {f_j} = F ->
      return [ Rewrite(v_j, false, A) | j = 1..m ]
    (g x1...xn), g in Inlinable, every x_i a symbol or literal ->
      (ps, body) := Inlinable[g]; q := param of g bound to acc
      return Reconstruct(body, A U {q}) # other ps -> wrapper
    p, p in A ->
      return [ VAR(p_f1)...VAR(p_fm) ]  # unchanged pass-through
    (if test then else) ->
      then_scalars := Reconstruct(then, A)
      else_scalars := Reconstruct(else, A)
      return [ (if test then_s else_s) | for then_s, else_s in zip(then_scalars, else_scalars) ]
    (cond [t1 e1]...[tN eN]) ->
      clause_scalars := [ Reconstruct(e_i, A) | for [t_i e_i] in clauses ]
      return [ (cond [t1 s_1]...[tN s_N]) | for s_1...s_N in zip(*clause_scalars) ]
    (case key [v1 e1]...[vN eN] [d_e]) ->
      clause_scalars := [ Reconstruct(e_i, A) | for [v_i e_i] in clauses ]
      default_scalars := Reconstruct(d_e, A)
      return [ (case key [v1 s_1]...[vN s_N] [d_s]) | for s_1...s_N, d_s in zip(*clause_scalars, default_scalars) ]
    (assoc p k1 v1...), p in A ->
      updates := {k_i -> Rewrite(v_i, false, A)}
      return [ updates[f_j] if f_j in updates else VAR(p_fj)
             | for f_j in F ]
    _ -> Fail
\end{lstlisting}

the scalar loop variable for field $f$, and \texttt{Inlinable} the table mapping

A reconstruction may be wrapped in single-form \texttt{bind}/\texttt{do} layers
(as in Figure~\ref{fig:overview}, where the \texttt{make-<point>} sits under
\texttt{(bind [dx 0.1 dy 0.2] \ldots)}). The walk peels these layers, rewrites
their initializers (which may themselves read accumulator fields), and re-wraps
the rewritten \texttt{recur} in the same layers, so names like \texttt{dx}
remain in scope for the field expressions using them.

Because the emitted \texttt{recur} lowers to a \texttt{psetq} over the loop's
(now $m$-way expanded) binding list, and both the binding list and every
\texttt{recur} are rewritten together, the loop stays internally consistent by
construction; no code-generator change is required.

\subsection{Interprocedural reach by inlining}
\label{sec:inline}

The accumulator rarely reconstructs itself with a literal constructor; more
often it is rebuilt by a helper, as \texttt{(recur (update-point p) \ldots)}---the
motivation for a lightweight interprocedural step that avoids a full
whole-program analysis. During transpilation, a
\texttt{compile-form} hook records every single-clause function whose body
reduces (through \texttt{bind}/\texttt{do} peeling) to a record constructor
into an \emph{inlinable} table, keyed by name.

When the reconstruction at a recur position calls an inlinable function
whose accumulator-carrying argument is the accumulator itself, the walk
inlines the callee's body in place. The parameter receiving the
accumulator joins the alias set, so reads of \emph{that} parameter inside
the inlined body (e.g.\ \texttt{(get p :x)} in \texttt{update-point}, whose
parameter is also named \texttt{p}) are recognized and rewritten to field
variables; other parameters bind via a wrapper layer around the
rewritten \texttt{recur}. Inlining applies only when the callee's arguments
are symbols or literals, keeping the substitution capture-free and
side-effect-safe. This one-level, syntactic inliner reaches the dominant
\texttt{(recur (helper acc) \ldots)} shape, composing with \S\ref{sec:loop}'s
peeling to turn Koka-style ``functional but in place'' record
threading into flat scalar arithmetic.

Unlike ownership- or effect-based approaches to in-place update
\cite{reinking2021perceus,lorenzen2023functional}, this unboxing and inlining
requires no type information: the inlinable table is populated purely from
syntactic shape, and the alias-set discipline keeps the rewrite local and
checkable. This makes it a suitable prerequisite for a subsequent
numeric-specialization pass (\S\ref{sec:eval}), which infers types for the scalars ASR exposes.

\subsection{Alignment by construction}
\label{sec:align}

The classifier and the rewriter are the \emph{same walk}: there is no separate
legality analysis that could drift out of sync with the
transformation, since the walk rewrites what it recognizes and aborts on
everything else. Soundness of the field-level rewrite is thus local and
obvious---every surviving accumulator reference is either a field read
(replaced by the corresponding scalar) or a tail re-box (replaced by an
equivalent constructor), and no bare accumulator escapes---one that
did would have aborted the walk---and the pass is conservative by
default: novel or complex accumulator uses prevent optimization
rather than risk a wrong rewrite. For a pass enabled on latently-typed
code with open-world dispatch, ``inapplicable'' is a far cheaper failure
mode than ``incorrect.''

We can state this guarantee precisely:

\noindent\textbf{Invariant (alignment).} \emph{If \texttt{Rewrite} returns
without raising \texttt{Fail}, then in the rewritten body every reference
to an accumulator-alias name has been
replaced by one of exactly three forms: (i) the scalar variable
\texttt{VAR}($p\_f$) of a field $f\in F$ (a field read); (ii) the per-field value
expressions spliced into a \texttt{recur} (a reconstruction); or (iii) the single
tail re-box \texttt{(make-<t> \ldots)}. No bare accumulator reference survives.}

\noindent The invariant holds by construction: those three are the only cases in
which \texttt{Rewrite} returns a term mentioning the accumulator, and every other
occurrence---a field read of an absent key, a bare accumulator in non-tail
position, an unrecognized reconstruction---is a \texttt{Fail} case. Two
corollaries follow. \emph{Allocation:} the only \texttt{make-<t>} reachable in the
rewritten loop is the exit re-box of case (iii), which post-dominates the loop and
runs at most once per activation, so the back-edge allocates nothing.
\emph{Correctness:} because the walk is total---it either succeeds with the
above shape or emits the original loop verbatim---the pass never yields a rewrite
outside these three equivalences, which is why it is safe on
untyped code without a separate legality analysis. This is a structural
exhaustiveness argument over the walk's own case analysis, not an
independent proof of semantic equivalence against a formal operational
semantics; each case's correctness is argued individually where it is
introduced (\S\ref{sec:loop}).

\subsection{Soundness under live redefinition}
\label{sec:world}

Aggregate scalar replacement bakes a class's field layout into the fast path: it
assumes \texttt{<point>} has exactly fields \texttt{x} and \texttt{y}. In FOL a
class can be redefined at run time---\texttt{(defclass <point> [] [[x] [y]
[z]])}---invalidating that assumption. We keep the optimization sound with
the same \emph{invalidation ladder} the transient work uses: a static
analogue of the assumption-and-deoptimization mechanism JITs
use for speculative optimization (\S\ref{sec:related}).

The converted loop is emitted as a guarded dual path (Figure~\ref{fig:emitted}).
At load time, a validity cell is registered and indexed under the record's
class name; \texttt{emit-defclass} is instrumented so that (re)defining a
class \emph{notifies} the world, flipping the cells of the regions
that assumed that class name. The guard---one pointer read of the cell's
\texttt{car}, checked once on loop entry---selects the unboxed fast path
while the assumption holds, the original loop after redefinition.
In-flight activations complete on the path they
entered, safe because the fast path performs only scalar arithmetic and
a final re-box against the field layout compiled for (concurrent
execution model made precise in \S\ref{sec:discussion}). When the compiler
is told the world is sealed (whole-program, cold-loaded builds), the guard
is omitted and only the fast path is emitted.

\section{Implementation}
\label{sec:impl}

The pass is implemented inside FOL's compiler in about 560 lines of Common Lisp:
roughly 450 in the core classify-and-rewrite walk (\S\ref{sec:loop}) that
unboxes a single accumulator, the remainder in the interprocedural
inlining/registration machinery of \S\ref{sec:inline} that this paper counts
as part of the same contribution.
It lives at the loop-emission boundary rather than as a standalone AST pass
because the transformation needs the class registry and the record
constructors that \texttt{defclass} populates during emission, and it reuses the
existing loop/recur code generator by handing it an already-rewritten loop node.
Its entry point is consulted by \texttt{emit-loop} before the transient path;
when it declines, emission proceeds unchanged, so a program that never
triggers the pattern produces identical output.

The inlinable-function table is populated by the same \texttt{compile-form} hook
that drives interprocedural summary inference; because forms transpile
in source order, a helper is registered before the loop that calls it. The pass
is gated behind a single flag; with it off, \texttt{emit-loop} is
byte-for-byte unchanged.

\section{Evaluation}
\label{sec:eval}

We evaluate four questions. \textbf{RQ1:} does the transformation fire on the
target pattern and eliminate allocation? \textbf{RQ2:} what speedup does it
deliver, and is the result identical to the unoptimized program? \textbf{RQ3:}
how close does the optimized code come to a native mutable-struct implementation,
and what accounts for the difference? \textbf{RQ4:} what does it cost when
disabled or inapplicable? All measurements ran on an AMD Ryzen 5 7430U
(single-threaded) with 32\,GB RAM, running SBCL 2.6.0---generational GC,
1\,GB dynamic space, 51\,MB nursery---on Windows 11. For each benchmark and
configuration we run one warm-up call followed by 20 timed calls, forcing a
full collection before each, and report the mean $\pm$ sample standard deviation.
Wall time uses the real-time clock; per-call allocation, GC counts, and GC
time are read from the SBCL runtime (the bytes-consed
counter, an after-GC hook, and \texttt{*gc-run-time*}); speedup is computed per
paired trial, then averaged. As an upper bound, we implement each
benchmark natively---an idiomatic mutable \texttt{defstruct} updated in place,
with declared \texttt{single-float} slots matching FOL's float type, compiled at
\texttt{(speed 3) (safety 0)}.

Because speedup over the baseline depends on how often the collector runs, it
carries run-to-run variation of roughly $\pm0.5\times$; the allocation figures
(deterministic) are the more robust numbers---wall-clock timings, native
ceiling included, are not. The fourteen benchmarks span three families. The first eight are
physics-simulation kernels exercising the core rewrite and its branch
shapes: a \emph{particle} simulation (two independent additive field updates,
the pattern of Figure~\ref{fig:overview}), a 2D \emph{rotation} orbit (two
fields, coupled multiplicative map), a three-field \emph{ballistic}
integrator (position update reads the freshly computed velocity), and a
coupled \emph{two-body} relaxation carrying \emph{two} \texttt{<vec2>}
accumulators, each reading both---the multi-accumulator case. A \emph{clamp}
benchmark demonstrates \texttt{if}-branched conditional reconstruction; a
\emph{bounce} benchmark demonstrates \texttt{cond}-branched reconstruction
with three syntactic clauses (a high-wall bounce, a low-wall bounce, and a
normal move)---the pass must classify all three to accept the
loop, though its trajectory only reaches the high wall and
normal move; a \emph{phase} benchmark demonstrates \texttt{case}-branched
reconstruction where the iteration index modulo 3 visits
all three clauses; and an
\emph{assoc} benchmark demonstrates partial reconstruction from a generic
\texttt{assoc} update, not a full constructor call. The next five are recognizable
kernels from different domains, varying field count and arithmetic
intensity: a \emph{Mandelbrot} orbit (image processing; two fields, quadratic
map), a 1D \emph{Kalman filter} (state estimation; two coupled
accumulators---a \{x,v\} estimate and a symmetric covariance---with per-step
division), a \emph{biquad} IIR filter (audio DSP; a four-field filter state),
streaming \emph{co-moments} (online covariance; four fields with running
division), and a \emph{Lorenz} attractor (chaotic ODE; three fields, a
temporary-free Euler step, the accumulator the only allocation). A final
\emph{Counter} benchmark is the simplest case: a single-field record
advanced through an inlinable helper, isolating the pass's fixed per-iteration
cost from field count and domain-specific arithmetic.

\textbf{RQ1: Firing and allocation.} The pass fires on all fourteen
benchmarks: each emitted fast path (Figure~\ref{fig:emitted}) splits every
record accumulator into one scalar loop variable per field, inlines any
update helper, and contains \emph{no} constructor call on the back-edge.
In two-body and Kalman, the fixpoint (\S\ref{sec:discussion})
unboxes \emph{both} accumulators; parallel \texttt{recur}/\texttt{psetq}
keeps the coupled update correct. Per iteration each baseline conses one
record (144--240\,B), or two (roughly 400\,B) in the multi-accumulator
cases---0.7--2.0\,GB per call, triggering 14--38 collections costing
17--53\,ms---whereas the scalar-replaced version conses \emph{nothing} and
triggers no workload collection; only the single exit re-box
survives, at most once per activation. Native, mutating in place, likewise
conses nothing.

\textbf{RQ2: Speedup and correctness.} Table~\ref{tab:speedup} reports
results for all fourteen benchmarks. Eliminating allocation removes the
garbage-collection pressure dominating each baseline, yielding end-to-end
speedups of 3.1$\times$--16.3$\times$. \emph{Assoc} alone accounts for the
top of that range: its update goes through FOL's generic \texttt{assoc}
dispatch rather than a specialized constructor, so its baseline is
both dispatch- and allocation-bound, unlike the other thirteen
benchmarks' direct constructor calls; ASR removes both costs at
once, reaching 16.3$\times$, more than double any other benchmark.
Excluding it, the remaining thirteen span a typical
3.1$\times$--7.0$\times$: physics-family kernels (Particle, Rotation,
Ballistic, Two-body, Clamp, Bounce, Phase) see 4.1$\times$--7.0$\times$
(Bounce's extra \texttt{cond} tests cost more than Clamp's single
\texttt{if}, making it lowest here), while arithmetic-heavier
kernels (Mandelbrot, Kalman, biquad, co-moments, Lorenz) see
3.1$\times$--4.6$\times$---the more a loop computes per step, the smaller
allocation's share of runtime and the win from removing it
(RQ3). Every optimized program returns results bit-identical to its
unoptimized counterpart across all five trials; a dedicated test suite
checks this on several record-accumulator shapes (field read at exit,
bare re-box, inlined and non-inlined reconstructions,
\texttt{if}/\texttt{cond}/\texttt{case} branches, coupled accumulators),
and the full compiler test
suite of 3{,}597 checks passes with the pass enabled.

\textbf{RQ3: Distance to native.} A hand-written native version---a mutable
\texttt{defstruct} updated in place---is 90$\times$--250$\times$ faster than the
persistent baseline (Table~\ref{tab:speedup}), which is what makes the pattern
worth attacking. (Whether a JIT closes this
gap without ASR is answered on real GraalVM measurements in
\S\ref{sec:discussion}.) Aggregate scalar replacement (ASR) recovers
the \emph{allocation} component of that gap: it removes 100\% of the per-iteration
consing, worth the 3.1$\times$--16.3$\times$ of RQ2. It does \emph{not} close the
gap entirely---the scalar-replaced loop remains 13$\times$--40$\times$ slower
than native, reaching 3--8\% of native speed. The decomposition is consistent
across all fourteen benchmarks: the allocation factor ASR removes (its speedup)
times the arithmetic factor left (its distance to native) equals the
baseline gap---a directly measured identity, not an estimate. By inspection
of the emitted code (Figure~\ref{fig:emitted}), the residual is
structurally two things: a per-\emph{activation} \textbf{construction}
call---the exit re-box's \texttt{make-instance}, executed exactly once
regardless of iteration count---and a per-\emph{iteration} cost of generic
arithmetic, since the unboxed loop still calls FOL's \emph{generic}
operators on its scalar variables where the native loop issues declared
single-float machine instructions. At these benchmarks' scale (5M
iterations), this asymmetry alone suffices to conclude the arithmetic
factor dominates: one amortized construction call cannot compete with
millions of per-iteration generic-arithmetic calls, whatever their
per-call costs. We do not independently measure the
two factors here; the 5$\times$--116$\times$
construction-overhead figures from a companion ELS'26
paper~\cite{adrian2026fol-els} were measured on different object shapes
and protocol---context, not a direct measurement here. This
also explains RQ2's speedup spread: arithmetic-heavier kernels
(Mandelbrot, Kalman, biquad, co-moments, Lorenz) spend a smaller share of
their time allocating, so removing allocation buys proportionally less. Closing the arithmetic gap
is the job of a complementary \textbf{numeric specialization pass}, implemented
in the compiler but orthogonal to this work: it seeds each
scalar's type from its literal initializer, propagates it through the
arithmetic to a fixpoint, and---wherever every operand is proven
numeric---lowers FOL's generic operators to native machine arithmetic on
declared floats. We measured it under the exact protocol of
\S\ref{sec:eval}, applied on top of ASR on Mandelbrot and Lorenz---the two
single-accumulator arithmetic-heavy kernels above (Kalman's two coupled
accumulators are a natural but separate case for future measurement)---plus
Particle as a control: 4.27$\times$ over ASR-only on Particle, 6.63$\times$
on Mandelbrot, 13.20$\times$ on Lorenz, confirming that arithmetic-heavy
loops gain most. Against native, this closes most of what ASR alone
left open: Mandelbrot and Lorenz fall from 24.2$\times$/34.9$\times$
(ASR-only) to 3.7$\times$/2.6$\times$; Particle falls from 18.7$\times$ to
4.3$\times$. Results are bit-identical to ASR-only throughout. The pass's
own design remains future work outside this paper's contribution, but
its effect on the residual gap is no longer unmeasured. Attacking allocation first is
nonetheless not arbitrary: it is the factor that produces garbage-collection
pauses (the baseline triggers 14--38 collections per call; ASR triggers none),
so it removes GC from the loop entirely---a latency benefit, not merely the
throughput factor the speedup measures---and is the prerequisite for the
arithmetic work, since the literal-seeded scalars ASR exposes are exactly what
make the type inference tractable.
\textbf{RQ4: Cost when disabled or inapplicable.} With the flag off, loop
emission is unchanged and output is byte-identical to the unmodified
compiler; there is no residual cost. When the flag is on but the pattern does
not apply---because the accumulator escapes, the reconstruction is not a
recognized shape, or the class is unknown---the walk aborts and the original
loop is emitted, again with no generated-code change. We verified the
abort path on an accumulator flowing into an unknown call: the loop is left
untouched and no scalar variables are introduced.

\textbf{Correctness under redefinition.} We exercise the world guard directly:
after a converted loop registers its region, redefining the record class flips
the region's validity cell, and the next call falls back to the original
allocating loop, still producing the correct result against the redefined
class.

\section{Discussion and Limitations}
\label{sec:discussion}

\textbf{Scope of the current transformation.} The pass unboxes \emph{every}
qualifying record accumulator in a loop via the fixpoint of \S\ref{sec:algo};
an accumulator failing to qualify is left boxed, so replacement is
per-accumulator, not all-or-nothing (the two-body and Kalman benchmarks
unbox two coupled records this way), and non-record loop variables pass
through unaffected. Genuine limitations remain: each reconstruction must
peel---through single-form \texttt{bind}/\texttt{do} wrappers and at most
one level of inlinable call---to a constructor supplying every field;
\texttt{if}-, \texttt{cond}-, and \texttt{case}-branched reconstructions
are all recognized directly (Table~\ref{tab:speedup} exercises all three:
Clamp, Bounce, Phase), but only when each branch's constructor is reached
without its own peeling or callee substitution---a branch needing either
aborts reconstruction.

\textbf{Relationship to partial escape analysis.} Partial escape analysis
with scalar replacement \cite{stadler2014partial} is strictly more
general: it handles arbitrary control flow and materializes objects
lazily where they escape. Our transformation trades that
generality for a simple, auditable rewrite specialized to the
loop-accumulator pattern, adding something a closed-world JIT does not
need: soundness under class redefinition. A promising direction is
generalizing the single classify-rewrite walk toward a
materialization-on-escape discipline while retaining the world guard.

\textbf{Freshness, not linearity.} Where Perceus \cite{reinking2021perceus}
and uniqueness/borrowing systems \cite{lorenzen2023functional} establish
in-place reuse through reference counting or types, we establish it
structurally: the accumulator is freshly constructed at loop entry and
every use is a field read or a tail reconstruction, so no live alias
survives a rewrite---in-place behavior, indeed no ``place'' at all,
without a type system, applying only where the syntactic
discipline holds.

\textbf{Execution model and concurrency.} The world registry is shared
mutable state: region registration and redefinition-triggered
invalidation are serialized by a single lock, while the emitted guard
itself is a single unsynchronized pointer read on the hot path, relying
on the flag never being revived once invalidated. We have not verified
this design under concurrent load or on weakly-ordered architectures
(only x86-64 is tested); a rigorous memory-model argument and a
concurrent stress evaluation are both future work. Invalidation is also
one-way: redefining a class even once permanently retires the fast path
for every dependent region until recompiled, so a workload that
redefines repeatedly rather than once at a REPL would fall back on every
call thereafter and recover none of ASR's benefit. We assume redefinition
is coarse and infrequent (a REPL or hot-reload action), the setting this
paper's guard targets.

\textbf{How common is the pattern? A Clojure corpus study.} Because FOL has no
user base, we estimate the pattern's incidence in Clojure---which shares FOL's
records, \texttt{loop}/\texttt{recur}, and persistent-update idioms---as a proxy.
A reader-level analyzer (released with the artifact) scanned 29 Clojure projects
across seven domains (2{,}905 files). Of 1{,}442 \texttt{loop}/\texttt{reduce}
accumulator sites, a record accumulator rebuilt each iteration appears in just 8
(0.55\%), and only 3 (0.21\%) in the strong form (rebuilt by constructor or
\texttt{assoc}). The pattern is rare---but its scarcity is itself suggestive:
primitive-scalar loops, the hand-written equivalent of ASR's output, outnumber it
27 to 1 and dominate the numeric and geometry code where records would
otherwise be natural (\texttt{fastmath} alone writes 39 primitive loops to 2
record ones). One reading is that the clean record style is avoided
\emph{because} it is slow---the cost this paper removes. A corpus count
cannot rule out an ordinary stylistic preference for primitive
loop-local state, unrelated to performance; we report the ratio as
suggestive, not evidence, and leave separating the two readings (author
interviews, or an explicit before/after refactor) to future work.

Hand-auditing the three strong matches sharpens the picture, and not in our
favour. All three are genuine record-accumulator loops in
real numeric and parsing code, yet each falls outside our pass: one
(\texttt{fastmath}'s Neville extrapolation, Figure~\ref{fig:wild}) accumulates through
\texttt{reductions}, which \emph{yields every intermediate}, so the accumulator
escapes and is not scalar-replaceable in principle; one reads its
\texttt{Vec2} accumulator inside a \emph{nested} loop; and one
(\texttt{datascript}'s pull-pattern parser) updates its record by \texttt{assoc}
under a macro. The currently-firable incidence is thus, in this corpus, at the
noise floor: the abstract pattern is rare, and even its clean instances carry
shapes our v1 walk does not handle. We draw two honest lessons: we do not
claim broad current impact, but the idiom occurs in real numeric
code, is at least consistent with the cost-avoidance reading above, and
points precisely at what to handle next---and, since the scan, we have:
nested-accumulator reads and \texttt{assoc} updates hidden behind a macro
are no longer learnable shapes but implemented and independently
measured on these exact two sites (Table~\ref{tab:reitit}, below), while
the \texttt{reductions} case remains the one fundamental limit---a
genuinely escaping accumulator. This is a Clojure proxy, not a measurement of FOL, and if
performance-aware Clojure hand-writes the scalar form where it matters,
this count is a lower bound on the pattern's true incidence---though, per
the confounds above, we cannot confirm that premise from the corpus alone.

A gate-faithful pass, ported from \texttt{src/compiler.lisp}'s actual
candidate/reconstruction/escape gates (\S\ref{sec:cand}--\S\ref{sec:loop})
the same way \S\ref{sec:discussion}'s own transient-conversion classifier
ports \texttt{src/escape-analysis.lisp}'s, and run mechanically over the
same 29-project corpus rather than by hand, confirms this reading exactly:
of 678 \texttt{loop} sites (the pattern's construct; FOL's loop-carried ASR
has no \texttt{reduce}-shaped analogue to port faithfully), \emph{one}
qualifies---\texttt{fastmath}'s nested-loop \texttt{Vec2} read, the same site
above, and no other. Finding only that one site mechanically, with nothing
missed and nothing extra, confirms the hand-audit was complete for this
corpus, not merely representative. The other two do not qualify, for two
distinct, now corpus-verified reasons rather than an inspection guess:
\texttt{fastmath}'s \texttt{reductions} case fails exactly as expected (no
gate recognizes a \texttt{reductions}/\texttt{reduce} chain as a
reconstruction); \texttt{datascript}'s pull-pattern accumulator turns out to
fail \emph{earlier and more specifically} than "hidden behind a macro"
suggested---its own \texttt{(defrecord PullPattern [attrs first-attr
last-attr reverse-attrs wildcard?])} declares five fields, but the loop's
own pre-loop init supplies only three, so the exact-field-set gate
(\S\ref{sec:cand}) rejects it before the macro-hidden \texttt{assoc} update is
ever reached---consistent with, not contradicting, this paper's own
practice of hand-porting corpus sites to a field-complete shape rather than
converting them verbatim (\S\ref{sec:discussion}, below). Two further
sites the classifier also finds record-shaped correctly decline for reasons
outside this pattern entirely: a pair of \texttt{data.avl} accumulators
update via \texttt{assoc!} (in-place transient mutation, a different
technique's territory, not a false negative here) and one
\texttt{datascript} site reconstructs through a helper call, the same
no-inlining limitation \S\ref{sec:discussion}'s transient classifier already
documents. The gate-faithful rate---1 of 678, 0.15\%---replaces what was
previously only a syntactic upper bound for this specific claim.

\textbf{Three real whole-program results.} The classifier also flags a weaker
tier---update via a \emph{helper} call rather than a bare constructor/
\texttt{assoc}---five more sites across the same 29 projects. Of these,
\texttt{reitit}'s route-\texttt{Methods} builder (a widely used Clojure HTTP
router) threads a 9-field record through \texttt{cond-> acc any? (assoc
method ...)} once per HTTP verb; recognizing the always-true \texttt{any?}
test, this is an unconditional \texttt{assoc}, the same shape as our own
Assoc microbenchmark. We ported it faithfully and re-ran its chain: results
are bit-identical across all 9 fields. Table~\ref{tab:reitit} reports the
measured cost at the same rigor as Table~\ref{tab:speedup} (mean $\pm$ sample
stddev over 20 trials): allocation drops 3.22$\times$ and wall time improves
4.58$\times$. The residual allocation is the single final record instance
ASR must construct at the chain's tail---baseline pays for that plus
eight intermediate ones ASR elides; both are single straight-line
constructions per call, not a hot loop, so not directly comparable
to the loop benchmarks' range. That hand-port is no longer necessary: a
small compile-time unrolling recognizes a \texttt{reduce} whose collection
argument is a literal---or, as with \texttt{http-methods} here, a top-level
\texttt{def} naming one---and rewrites it into the identical bind chain
before the pass runs, so the un-ported source reaches the same
transformation; we verified this functionally on the pattern
above (bit-identical output), though we did not re-run
Table~\ref{tab:reitit}'s timing on this new entry path.

The other two of the corpus study's three hand-audited strong matches
(above) are ported the same way---faithful shape (real field count and

\textbf{Novelty, and why an open world.} We claim no new escape analysis:
holding a non-escaping object's fields in variables is classical
\cite{choi1999escape,stadler2014partial}. What is new is the \emph{assembly} and
its target---loop-carried unboxing of persistent records, reached
interprocedurally by a one-level syntactic inliner and kept sound under
\emph{live class redefinition} by a per-region validity guard---in a transpiled,
latently-typed language with no optimizing IR, no JIT, and no type system.
The open world is not incidental here; it is what creates the problem the
guard solves. A JVM language such as Clojure has the identical allocation pattern
(a \texttt{defrecord} rebuilt through \texttt{loop}/\texttt{recur}) but compiles
records to classes not redefined mid-run, so it faces no version of
the redefinition problem our guard solves. Its JIT's partial escape analysis
\cite{stadler2014partial} could in principle eliminate the same
allocation---we tested this directly, on GraalVM's Graal compiler, with
warm-up to let tiered compilation settle. On this paper's own Particle pattern
(Figure~\ref{fig:overview}: a 2-field \texttt{defrecord} threaded through
\texttt{loop}/\texttt{recur} via one helper call) declared with primitive
type hints on its fields, Graal eliminates the allocation entirely---24\,B/call,
matching a hand-written primitive-double loop
(1.02$\times$ its time). Removing the hints---an untyped
\texttt{defrecord}, the idiomatic default and what \texttt{reitit}'s real
source and this corpus use---changes the outcome completely on
the identical loop: Graal eliminates nothing, 48\,B/iteration (vs.\ the
typed case's fixed 24\,B \emph{per call}, not per iteration), 5.7$\times$
native---warm-up buys no meaningful benefit here. On \texttt{reitit}'s own
9-field \texttt{assoc}-chain shape (Table~\ref{tab:reitit}'s pattern,
likewise untyped), Graal again eliminates nothing: 640\,B/call survives.
The determining factor across all three tests is field typing, not loop
or call shape: Graal's escape analysis succeeds only when hand-added
primitive hints are present, which \texttt{defrecord} does not
require and idiomatic code, \texttt{reitit} included, does not have. FOL's
mechanism needs no such hint and fires identically on typed and untyped
records, so the comparison that is apples-to-apples---untyped
against untyped---has a production JIT with state-of-the-art partial
escape analysis leaving the allocation in place on both the simple and
real-world shape, while FOL's static mechanism removes it on both.
A statically typed
language such as Koka attacks the same cost from the opposite
direction, with reference counting and borrowing
\cite{reinking2021perceus,lorenzen2023functional} presupposing the type
information FOL lacks. The gap we address---allocation-eliminating scalar
replacement for records in an \emph{open-world, untyped, JIT-less}
setting---is precisely the one those systems leave open; the mechanisms
(region invalidation, safe-by-abort emit-time rewriting), not FOL itself,
transfer to other transpiled dynamic languages.

\textbf{Extending the pattern to plain maps.} \texttt{reitit}'s accumulator is
a \texttt{defrecord}, but Clojure's idiomatic default for exactly this
fixed-small-key-set shape is a plain, schema-less map---\texttt{defrecord} is
opt-in, chosen for protocol dispatch or type-checked construction, not
required for ordinary data threading. A targeted follow-up scan for map-typed
analogues of the record pattern---an accumulator seeded \texttt{\{\}} and
touched only by literal-keyword \texttt{get}/\texttt{assoc}---found no large
hidden population behind our classifier's record-only lens: just six sites,
all trivial one- or two-key maps. That null result is informative
(our classifier is not undercounting a bigger effect), but it does
not settle the question a FOL implementor
faces: a programmer writing \texttt{reitit}'s builder the idiomatic way,
against \texttt{\{\}}, got none of ASR's benefit merely for not
committing to a \texttt{defclass}.

We close this gap with \texttt{*DICT-SCALAR-REPLACEMENT*}, an
independently-flagged extension to the same intra-bind rewrite. Records
resolve their field set from a pre-registered \texttt{defclass} schema; dicts
have none, so this mode discovers it from usage---every touch must be
a literal-keyword \texttt{get}/\texttt{assoc}, never a dynamic key---then
scalarizes and reboxes exactly as before, under the same world-guard. The
full regression suite (3{,}597 checks) remains 100\% green with the extension
enabled.

Re-running \texttt{reitit}'s chain verbatim, with \texttt{\{\}} in place of
\texttt{(make-<methods> ...)}, results remain bit-identical across all 9
fields (Table~\ref{tab:reitit}, second row): allocation drops
1.89$\times$ and wall time improves 1.72$\times$. Both figures are smaller
than the \texttt{defclass} case (3.22$\times$/4.58$\times$), and
Table~\ref{tab:reitit}'s numbers show why: the final rebox both modes
still pay for is comparable in absolute terms (1324.7\,B record,
1486.5\,B dict), so the gap is entirely in what each baseline pays for its
eight eliminated intermediate touches---(4265.7$-$1324.7)/8 $\approx$
367.6\,B per touch for a full record slot-vector rebuild versus
(2812.6$-$1486.5)/8 $\approx$ 165.8\,B per touch for a HAMT map update.
Baseline dict allocation starts lower per touch, so there is proportionally
less for ASR to eliminate. The result is smaller, not zero: a real
programmer following Clojure's actual idiom for this shape now gets a
real, verified speedup without first learning---or even knowing
about---ASR's record-shaped precondition.

\textbf{Portability: four further host languages.} The claim that our
mechanisms---not FOL itself---transfer to other transpiled dynamic
languages is not merely argued here: we built four further
existence-proof ports, each independently reimplementing qualification
and rewrite against that host's own AST and loop construct---CPython
(reference-counted heap, no JIT), Erlang/BEAM (immutable-by-default,
clause-dispatch tail recursion in place of \texttt{loop}/\texttt{recur}),
Julia (an LLVM-based JIT with its own escape analysis), and Ruby (a
mark-and-sweep-GC'd heap, no unparser for its own AST, and---uniquely
among the five---two independent redefinition vectors requiring two
separate guard-hook families)---and ran the same two-pass corpus
methodology used above (a syntactic Pass~1 upper bound, then a
gate-faithful Pass~2 that runs each port's real, shipped transform as a
black-box oracle, never a re-implementation that could drift) against
each host's own real code. Appendix~\ref{sec:ports} reports full
per-language corpora, methodology, and results (Table~\ref{tab:ports});
the headline findings:

\emph{The mechanism transfers cleanly.} All four ports pass dedicated
test suites exercising the shapes described in \S\ref{sec:algo}---direct
reconstruction, interprocedural inlining, branch-shaped reconstruction,
multi-accumulator fixpoints---plus, for CPython and Julia, direct field
mutation of a non-frozen accumulator, a shape FOL's own always-immutable
records never required. The world guard itself transfers unevenly: Julia
needs none at all (struct redefinition is a hard compile-time error),
CPython and BEAM each need one hook, and Ruby needs two independent ones
(Appendix~\ref{sec:ports}'s Ruby subsection)---the guard's own
complexity tracks each host's own redefinition surface, not the
rewrite's.

\emph{Payoff is conditioned on whether the host already does this.}
Where no competing allocation-elimination exists---CPython, Erlang/BEAM,
Ruby, and FOL itself---synthetic benchmarks instantiating the same
fourteen patterns as Table~\ref{tab:speedup} show real, substantial
speedups: CPython 2.95$\times$--35.64$\times$, FOL
3.1$\times$--16.3$\times$ (\S\ref{sec:eval}), Ruby
3.07$\times$--16.74$\times$, BEAM 1.01$\times$--1.80$\times$. Julia is
the exception: its JIT already performs SROA-style escape analysis, so
13 of 14 ported benchmarks measure near 1.0$\times$---nothing is left to
eliminate---and one (Kalman, the same coupled two-accumulator shape as
this paper's own Table~\ref{tab:speedup} entry) measures a 0.87$\times$
regression: ASR's own parallel-update staging costs more than the
allocation it removes once the host compiler was going to remove that
allocation anyway.

\emph{Real-code incidence is low everywhere except where the host forces
it.} Gate-faithful (not syntactic) qualifying rates: CPython 0 of 9 raw
candidates (0.00\%) across 10{,}074 files/27 projects; Julia 1 of 247
(0.4\%) across an \emph{exhaustive} scan of Julia's own standard library
(365 files---not a sample); Ruby 0 of 0 genuine candidates across 2{,}236
files/18 projects---Pass~1 itself never surfaces a real
\texttt{Struct}/\texttt{Data.define}-shaped candidate at all, the
sharpest form of this finding yet; Erlang/BEAM 6 of 41 (14.6\%) across 30
files from one project family (Erlang/OTP), after six targeted fixes.
BEAM's own outlier status is informative, not noise: Erlang has no
mutation at all, so a loop-carried accumulator has nowhere to go but
reconstruction, an opaque map, or a hand-optimized primitive---no third
option. CPython, Julia, and Ruby all have a rich mutate-via-method-call
or hand-written-class idiom (Python's \texttt{line.append\_safe(...)};
Julia's \texttt{IOBuffer}/\texttt{write}, \texttt{Ref}; Ruby's own
overwhelming preference for a hand-written class with \texttt{attr\_}
\texttt{accessor} over \texttt{Struct.new}/\texttt{Data.define}, even in
projects that use the declared-fields style elsewhere), and every one of
their real-world qualifying rates collapses toward zero even after
CPython and Julia each added direct support for exactly that mutation
idiom---most hand-written Python classes' constructors are not the flat,
inferrable shape either port's qualification requires, and Julia's own
investigation, reading seven real declining sites directly rather than
inferring from counts, found every one mutated through an opaque method
on a data structure with no fixed field count (a buffer, an array), a
shape no amount of interprocedural reach could ever flatten to scalars.
The record-accumulator pattern is genuinely rare in all three languages,
for a reason with a real causal story, not a Pass-1 measurement
artifact---the same reading \S\ref{sec:discussion}'s Clojure study
already gave for the 27:1 primitive-vs-record suppression ratio, now
independently corroborated in three more languages, two by the same
opaque-mutation mechanism and one (Ruby) by the declared-fields style
simply never being chosen for a loop-threaded accumulator to begin with.

\emph{Two more negative results, two more distinct causes.} Beyond
Julia's host-already-did-it regression, Erlang/BEAM's own corpus-derived
real-code benchmark (\texttt{httpc:validate\_headers/3}, extracted
verbatim, its full 39-field production record) regresses 2.5$\times$
(0.40$\times$)---not because BEAM optimizes the allocation away, but
because the loop itself is a short, bounded, two-hop normalization with
no long inner loop to amortize ASR's own field-splice-and-rebox cost
against; and Julia's one real, verbatim-qualifying site
(\texttt{Sockets.listenany}, its full production retry loop) eliminates
zero allocation despite qualifying and rewriting correctly, because its
accumulator escapes into an opaque call \emph{inside} the loop body on
every iteration, not just after it, so the rewrite must re-box a fresh
value at that call site each time---the mechanism did exactly what it
should given where the escape actually sits. Three structurally distinct
reasons a correctly-qualifying, correctly-rewritten instance of this
technique can still fail to pay off---host already did it, loop shape
does not amortize the rewrite, escape point is mid-loop rather than at
exit---none of them a defect in the mechanism itself, and none visible
from qualification alone; only running the benchmark shows which applies.

\textbf{Threats to validity.} External: FOL has no outside user base, and
our fourteen benchmarks are authored microbenchmarks instantiating the
target pattern, not corpus-sampled programs (\S\ref{sec:eval});
the Clojure study is a proxy for incidence, not a measurement of FOL.
We no longer argue mechanism transfer without demonstrating it: four
further ports (above, Appendix~\ref{sec:ports}) confirm it in languages
spanning reference-counted, clause-dispatch, JIT-compiled, and
mark-and-sweep-GC'd runtimes.
What remains open is narrower: FOL's own Clojure proxy now has a
gate-faithful ASR-specific pass (\S\ref{sec:discussion}), ported from
\texttt{src/compiler.lisp}'s own gates and run mechanically over the same
29-project corpus---1 of 678 \texttt{loop} sites (0.15\%) qualify, the
same single site the paper's own hand-audit already found, confirming
that audit was complete rather than merely representative---but this
measures \texttt{loop}/\texttt{recur} sites only; FOL's ASR pass has no
\texttt{reduce}-shaped analogue to port, so \texttt{reduce}-carried record
accumulators (like \texttt{reitit}'s own route builder, \S\ref{sec:discussion})
remain a syntactic-only estimate for this specific corpus, not a
gate-faithful one. The Erlang corpus is a single project family (OTP's
own house style), not independently-authored code the way the Python
and Clojure corpora are; none of the four corpora are randomly sampled
at web scale. Internal: speedups are single-machine wall-clock
measurements whose baseline is GC-scheduling sensitive; we mitigate this
with repeated trials and reported variance, but not by pinning the OS
scheduler or sweeping microarchitectures. A corpus study over real FOL
programs---cheaper than a full new port, reusing the infrastructure
already built for the Clojure proxy---is the experiment that would most
strengthen the claims that remain.

\section{Related Work}
\label{sec:related}

\textbf{Scalar replacement and escape analysis.} Scalar replacement of
non-escaping objects is classic \cite{choi1999escape,blanchet2003escape}; the
state of the art is partial escape analysis in a JIT, performing scalar
replacement along paths where an object does not escape and materializing it
where it does \cite{stadler2014partial}. Our work adapts the core
idea---hold an object's fields in variables---to a persistent-first,
open-world dynamic language, specializing to loop accumulators and adding
run-time-redefinition soundness.

\textbf{Object inlining and aggregate scalarization.} Further ways
compilers unbox aggregates border our work. \emph{Object inlining} fuses a
referenced object into its parent, removing an indirection and an
allocation \cite{dolby2000automatic}; we dissolve the record into
loop-local scalars instead. Production \emph{SRA} (LLVM's SROA, GCC's
SRA) splits a memory-resident aggregate into scalars once known not
to escape, over a typed SSA form and a fixed struct
layout; ours runs on untyped surface syntax over a layout that may change
under the running program---which the world guard tolerates. Functional
compilers reach a similar shape from the opposite direction: GHC's
\emph{worker/wrapper} transformation splits a function into a
scalar-argument worker and a boxing/unboxing wrapper at the boundary,
licensed by strictness analysis over a typed, closed-world
IR \cite{gill2009worker}---close to our per-field split and exit re-box,
but driven by demand analysis rather than a syntactic accumulator match.
Industrially, the JVM's \emph{Valhalla} project targets the same
allocation via a language change: a \texttt{value class} is a new,
statically opt-in type the JVM may flatten \cite{goetz2021valhalla}. Ours
is the opposite trade---no new type, no opt-in, applying transparently to
ordinary redefinable classes---at the cost of firing only on this
paper's syntactic loop-accumulator shape.

\textbf{Speculation, assumptions, and deoptimization.} The world guard is a
static analogue of the assumption-and-invalidation machinery adaptive
JITs use for speculative optimization: compile under an assumption
(e.g.\ a class is never subclassed, licensed by class hierarchy analysis
\cite{dean1995cha}), install a dependency, and on violation
\emph{deoptimize}, rewriting in-flight
activations back to interpreter frames \cite{holzle1992deopt}, as
production VMs do for devirtualized or inlined code
\cite{paleczny2001hotspot,detlefs1999inlining,duboscq2013speculative}.
Aggregate scalar replacement lives in the same design space but resolves
it differently: it is \emph{static}, emitting fast and fallback paths
ahead of time and selecting between them with a one-word guard rather
than compiling one speculative version and reconstructing frames on
failure; and invalidation is \emph{region-scoped}, not method-scoped,
sound because the fast path touches the redefinable layout at exactly one
point, the exit re-box. JIT techniques buy generality (any assumption,
switchable mid-execution) at the price of a runtime, a deoptimization
framework, and frame metadata; we buy a zero-dependency emit-time rewrite
at the price of switching paths only at loop entry.

\textbf{Guards and redefinition without a JIT.} Three further comparators
share this paper's JIT-less setting from different angles. \emph{Quickening}
replaces a generic bytecode with a type-specialized variant behind a guard
that falls back on a type mismatch, giving speculative fast paths inside a
bytecode interpreter with no JIT \cite{brunthaler2010efficient};
CPython's specializing adaptive interpreter (PEP 659) is a production
descendant. It guards individual operations on observed operand shape,
re-specializing continuously; we instead guard a whole aggregate's field
layout once, ahead of time, invalidated only by explicit redefinition,
with no per-operation guard on the fast path. Statically
compiled Scheme systems solve an adjacent problem by compiling a mutable
top-level binding to a heap-allocated \emph{box}, so later redefinition
is visible through every existing reference without recompiling them
\cite{kranz1986orbit}---the same open-world problem, but for a single
scalar binding, solved by permanent indirection rather than a
validity-checked fast/fallback pair. And CLOS itself already has a slower,
general answer for compiled code: redefining a class triggers
\texttt{update-instance-for-redefined-class} against every existing
instance \cite{kiczales1991art}. Our guard does not replace that
protocol---FOL still relies on it for instances our transformation
declines to touch---it just avoids paying it on the hot path our pass
recognizes.

\textbf{In-place update of functional data.} Perceus achieves garbage-free
reuse via precise reference counting \cite{reinking2021perceus}; borrowing
and uniqueness extend it to ``functional but in-place'' programming
\cite{lorenzen2023functional}. Linear types \cite{wadler1990linear} give a
type discipline for single-use values; Clojure's transients
\cite{hickey2008clojure} expose in-place update as a manual, unchecked
escape hatch. We target the same allocation cost but require neither
types nor annotations, eliminating the object rather than mutating it.

\textbf{Persistent data structures.} Hash array mapped tries
\cite{bagwell2001ideal} and their optimizations \cite{steindorfer2015optimizing}
underlie FOL's persistent collections. Deforestation
\cite{wadler1990deforestation} similarly removes intermediate structures,
but by fusing producers and consumers, not by unboxing a loop-carried
aggregate.

\section{Conclusion}

Persistent records make programs clear but allocation-heavy. The problem
this paper solves is not that fact alone---classic scalar replacement
already removes this allocation in a closed world---but that
neither of SRA's two assumptions, lexical scope and a class shape fixed
forever, holds for a loop-carried accumulator in a transpiled, JIT-less,
redefinition-capable language like FOL. We showed such an accumulator can
still be unboxed into scalar loop variables---no allocation on the
back-edge, one re-box at exit---by a single classify-and-rewrite walk
that reaches across a call boundary through a one-level syntactic inliner
and stays sound under class redefinition through a world guard, aligned
by construction so any unrecognized shape is declined rather
than miscompiled. That mechanism, not any speedup number, is the paper's
central claim.

We evaluated it accordingly, on both axes. Across fourteen allocation-bound
microbenchmarks it eliminates per-iteration allocation for
3.1$\times$--16.3$\times$ speedups, recovering the allocation component of
a 90--250$\times$ gap to native mutable structs. A Clojure corpus study
finds the target pattern rare (0.55\% of loop/reduce sites)---plausibly,
not conclusively, because idiomatic Clojure already hand-writes the
primitive-scalar form this pass would otherwise produce, at a 27:1
ratio; an ordinary stylistic preference unrelated to performance remains
a live alternative on this evidence. Rarity alone would leave the
mechanism unproven, so where the pattern occurs we did not stop at
counting it: Table~\ref{tab:reitit} measures three of the corpus study's
real hits, unmodified in shape, including a router library's whole
record-accumulator builder both as declared and as its idiomatic
schema-less-dict form, at full rigor. We read this as rarity being
a symptom of the cost removed, not evidence against removing it: doing
this \emph{safely} is what should transfer elsewhere, not the speedup
figures. We see ASR as transient conversion's record-shaped complement,
and a step toward open-world partial escape analysis.

The corpus (27 actively-maintained projects, 10{,}074 files, chosen to
mirror the Clojure study's seven domains: numeric, graphics/games, data
structures, language/compilers, web, tooling) finds the syntactic
pattern more often than the Clojure proxy (5.05\% vs.\ 0.55\% of
sites)---Python's own direct-mutation idiom accounts for 43\% of those
sites, with zero using \texttt{dataclasses.replace}---but the
gate-faithful pass, even after four rounds of targeted fixes
(module-qualified construction, annotated self-assignment, interspersed
attribute docstrings, defaulted constructor arguments), still finds
zero of nine raw candidates qualifying. Sampling 53 record-accumulator
classes across five of the largest projects found zero using
\texttt{@dataclass}: every one is a hand-written class with its own
\texttt{\_\_init\_\_}, and the port's field-inference only accepts an
\texttt{\_\_init\_\_} body that is a flat, unconditional sequence of
\texttt{self.<name> = <name>} assignments---real bodies routinely
compute derived fields, coerce types, or call \texttt{super().\_\_init\_\_()},
any of which aborts inference before mutability or escape analysis is
even reached. Hand-tracing all nine candidates found a mix of the
already-known aliased-reference limit (an accumulator passed bare to a
function, e.g.\ \texttt{mypy}'s \texttt{class\_info}), a
Python-specific analogue (a \emph{method} called on the accumulator
rather than a field access---\texttt{black}'s
\texttt{current\_line.append\_safe(...)}, since a Python object may
have real behavior, not just data), and two newly-characterized
structural limits with no Clojure analogue: an accumulator that changes
class across iterations (\texttt{LibCST}'s \texttt{Name}$\to$\texttt{Attribute}
rebuild), and a reconstruction that embeds the accumulator's own prior
value as a field of its replacement (building a left-leaning tree,
structurally incompatible with flattening to scalars regardless of
analysis power). None of the nine sites port verbatim; five were
adapted (faithful field count and shape, non-shape-relevant payload
stubbed, matching this paper's own \texttt{reitit}-adjacent hand-ports)
into working, independently measured benchmarks.

\subsection{Erlang/BEAM}

A \texttt{parse\_transform} port targets Erlang's only iteration
construct, tail-self-recursive functions, recognizing a record
constructed or updated at the tail call itself, reached across a
helper-call boundary the same way, and branch-shaped (guarded
multi-clause) reconstruction, which BEAM's own clause dispatch already
provides for free---no new transform code was needed for the analogue
of this paper's \texttt{if}/\texttt{cond}/\texttt{case}-branched
reconstruction (\S\ref{sec:discussion}). The corpus (30 files, one per
Erlang/OTP application, chosen for domain representativeness across
$\sim$20 domains, not cherry-picked for hits) initially qualified zero
of 41 record-shaped candidates; six targeted fixes across three
iterations---record-declared-default support for an omitted
constructor field, relaxing the base-case gate to allow the
accumulator's one remaining bare occurrence anywhere in a clause rather
than only in trailing position, a head-alias pattern that both binds
the whole accumulator and destructures a field in the clause pattern,
a literal-sub-pattern guard conversion, indirect entry construction
(the accumulator arriving as an already-bound variable or update
expression rather than a literal at the call site), and update-expression
transparency in the general use-classifier---brought six of 41 (14.6\%)
to qualifying. Every fix was independently verified by dedicated EUnit
fixtures before being credited; real OTP functions this size (7--40
clauses) routinely stack more than one qualification-blocking idiom at
once, so a single fix rarely flips a whole function on its own (of
eight candidates a single fix was expected to unlock, only one flipped
immediately; the other five needed a second, independent fix; two
remain out of scope---one a genuine multi-bare-use, one requiring real
interprocedural purity analysis to verify a helper does not misuse the
accumulator). Four of the six now-qualifying sites were extracted
verbatim (full production records: a 40-field \texttt{\#xmerl\_scanner\{\}}
for three xmerl scanning functions, a 39-field \texttt{\#http\_request\_h\{\}}
for one httpc normalization) into independently measured benchmarks,
surfacing a genuine rewrite bug the gate-faithful oracle's arity-only
qualification check could not see (an embedded self-call inside a
\texttt{case} branch was not updated to the function's new arity---fixed,
with a regression fixture). Three of the four measure real speedups
(1.13$\times$--3.90$\times$); the fourth, \texttt{validate\_headers/3},
regresses 2.5$\times$ (0.40$\times$)---not a host-already-optimized
result but a loop-shape mismatch: a short, bounded, two-hop
normalization with no long inner loop to amortize the cost of splicing
in one field-read expression per field (all 39, unconditionally, since
this port's indirect-entry-construction support has no
which-fields-are-actually-touched liveness analysis) against.

\subsection{Julia}

A macro-based port (\texttt{@asr function ... end}) recognizes both
loop constructs Julia offers---\texttt{while} and, added after the
corpus study below showed 86\% of loop-bearing functions were never
even scanned for the pattern (Julia's own idiom overwhelmingly favors
\texttt{for}, 81\% of all loop sites vs.\ 14\% \texttt{while}-only),
\texttt{for}---plus interprocedural reach generalized from one level to
a depth-bounded, memoized, cycle-safe recursive summary (closing a
latent soundness gap the generalization itself surfaced: a callee that
mutates a field, not just reads it, could otherwise have been wrongly
verified safe by a check designed only for read-only pass-through), and
direct field mutation on mutable structs. The corpus (Julia 1.10's
entire standard library---\texttt{Base} plus 12 stdlib modules, 365
files---scanned \emph{exhaustively}, not sampled, since it is small
enough to cover completely) finds 247 syntactic candidates, of which
exactly one qualifies under the real transform: \texttt{Sockets.listenany},
a port-retry loop threading an \texttt{InetAddr} record. Getting even
this one candidate to qualify took five extensions across the syntactic
upper bound's own investigation---parametric struct support, a
loop-body dispatch fix, and the interprocedural generalization above,
each independently motivated and verified by real code, none moving
the corpus's own qualifying count until the third closed the specific
combination \texttt{Sockets.listenany} needed. The remaining 246
candidates were investigated directly, not merely counted: seven real
declining sites were read across every domain sampled (arrays, compiler
internals, REPL, a parser, linear algebra), and all seven mutate
through an opaque method call on a data structure with no fixed field
count---an \texttt{IOBuffer} written a byte at a time, a parser state
advanced by its own \texttt{parse!}, a \texttt{Ref} passed as a
foreign-call out-parameter---never through direct field assignment, a
finding independently confirmed corpus-wide (zero hits for the
syntactic scanner's own mutation-shaped candidate category across
272{,}688 lines). This is a shape no amount of interprocedural
reach could flatten to scalars, since there is no fixed scalar field
set to begin with. Running the fourteen ported synthetic benchmarks
found 13 of 14 within measurement noise of $1.0\times$ and one
regression (Kalman, the same coupled two-accumulator shape as this
paper's own benchmark of that name, 0.87$\times$)---confirmed via
\texttt{@allocated} to already be zero-allocation on both the baseline
and transformed code, so this is pure rewrite overhead (parallel
temp-then-assign staging) with no allocation win to offset it against,
not a failed transformation. The one real, verbatim-qualifying site was
independently benchmarked by re-parsing and transforming the installed
Julia's own standard-library source directly, never hand-transcribed:
it eliminates \emph{zero} allocation (1200 constructions measured on
both the baseline and the transformed path, across 200 calls each
forcing five retries) despite qualifying and rewriting correctly,
because its accumulator escapes into the retry loop's own opaque guard
call (\texttt{bind(sock, addr)}) on every iteration, not just once at
exit, so the rewrite must re-box a fresh value at that call site each
time---confirmed by instrumented counting, not assumed from reading the
rewritten code.

\subsection{Ruby}

A source-splicing port targets Ruby's own \texttt{Data.define}/
\texttt{Struct.new} value types, recognizing direct or \texttt{\#with}
reconstruction, one-level interprocedural inlining, branch-shaped
(\texttt{if}/\texttt{elsif}/\texttt{else}) reconstruction, and---unlike
any other port here---a genuine multi-accumulator fixpoint, threading
two or more coupled accumulators (e.g.\ a Kalman filter's state and
covariance) through the same loop and cross-substituting each other's
field reads. Ruby's own parser (Prism) exposes no AST-to-source
unparser at all, unlike Julia's \texttt{Expr} printing, Python's
\texttt{ast.unparse}, or Erlang's Forms; every rewrite is instead a
\texttt{(start\_offset, end\_offset, text)} edit queued against the
\emph{original} source and applied highest-offset-first, so a statement
that never touches the accumulator survives byte-for-byte---safer than
a general unparser (correctness need only hold for the narrow shapes
this pass edits) at the cost of building that machinery once, up front,
that every other port gets for free from its host's own reflection.

Ruby's world guard is the most involved of the five, for a real
reason: Ruby has \emph{two independent} redefinition vectors, not one.
Reopening a class (\texttt{class Point; def x; 999; end; end})
retroactively changes an already-existing instance's behavior, since
Ruby method dispatch is always late-bound on the live class
object---the same vector FOL, CPython, and Julia each guard with a
single hook. But reassigning the constant a class is bound to
(\texttt{Point = Data.define(...)} again) silently rebinds the name to
a brand-new class object \emph{without touching any existing instance
at all}---a vector none of the other four ports have, since Ruby is the
only one where a class's own name and its own identity are separably
mutable. A single hook cannot see both: \texttt{method\_added}/
\texttt{method\_removed}/\texttt{method\_undefined} on the tracked
class's own singleton class catch the first; \texttt{const\_added} on
its owning namespace catches the second, since the old class object is
never itself touched by a constant reassignment. Both were confirmed
necessary by direct construction before the guard was written, not
assumed from the other ports' own designs, and a Ruby-specific
correctness subtlety followed directly from testing it: after a
constant reassignment, the guard's fallback path must reproduce the
\emph{same} failure unmodified Ruby code would hit (Ruby's constant
lookup is always late-bound, so even the untransformed method
re-resolves the constant fresh on every call and fails identically)---
the guard's job is matching what unmodified code does, not making code
immune to a real semantic-breaking change.

The corpus (18 actively-maintained projects, 2{,}236 files, five
domains chosen to mirror the other ports' own domain coverage as
closely as Ruby's ecosystem allows: data structures, web, language
tooling, numeric/graphics, general tooling) finds 266
\texttt{while}/\texttt{until} loop sites---the only loop shape
Ruby-asr's transform recognizes---of which exactly one syntactically
resembles a record accumulator (0.38\%), and that one is a confirmed
false positive: an unqualified same-project class-name collision
(\texttt{Dir.pwd} misclassified because an unrelated cop class
elsewhere in the same 934-file project happens to be named
\texttt{Dir} too), independently confirmed to decline both by
inspection (no \texttt{.members}) and under the real gate-faithful
oracle. Zero genuinely \texttt{Struct}/\texttt{Data.define}-shaped
types were found threaded through a loop at all, even though the
corpus's own projects define plenty elsewhere (rubocop alone declares
25)---the sharpest form yet of this paper's recurring finding that
idiomatic object-oriented code overwhelmingly prefers a hand-written
class over a declared-fields type, sharper even than CPython's own 0-of-9
result, since Ruby's Pass~1 does not surface a single genuine candidate
to begin with. Pass~2 (\texttt{gate\_check.rb}) runs the real,
unmodified \texttt{Asr::Transform.rewrite\_method\_source} as a
black-box oracle, but never loads or executes a single line of corpus
code: each candidate's declared field list is read from its own AST,
then registered as a throwaway \texttt{Struct.new(*fields)} stub inside
a fresh, per-file module, against which the real transform is invoked
on the candidate's own extracted method source---gate-faithful without
running untrusted code, possible only because Ruby-asr's own
qualification depends solely on \texttt{klass.respond\_to?(:members)},
never on a class's real behavior. This safety design has one
documented blind spot, discovered by sanity-checking the harness
against Ruby-asr's own known-qualifying benchmarks before trusting the
corpus result: a candidate reconstructed through an interprocedurally
inlined helper (\S\ref{sec:inline}) cannot be
gate-checked at all, since resolving the helper requires it to be
loaded in the running process, which the safety design deliberately
never does---an honest undercount with no effect on this corpus's own
zero-candidate result, but a real one. A secondary, descriptive-only
metric puts the zero finding in context: 139
\texttt{\#reduce}/\texttt{\#inject}/\texttt{\#each\_with\_object} call
sites were found across the same corpus, more than half the
\texttt{while}/\texttt{until} count, entirely outside what either pass
can see, since Ruby's own iteration idiom leans heavily on block-based
accumulation---an even sharper version of the gap Julia's own corpus
study surfaced mid-investigation (\texttt{for} loops, added after the
fact once found to dominate).

Running the fourteen ported synthetic benchmarks found real speedups
across the board, 3.07$\times$--16.74$\times$, with allocation reduced
by four to five orders of magnitude (200,000 iterations down to a
handful of objects per call)---MRI has no JIT and no competing
allocation elimination, so this sits with CPython's and BEAM's own
results rather than Julia's. Measuring that allocation reduction
needed a Ruby-specific accommodation: wrapping the tracked class's own
\texttt{.new}/\texttt{\#with} to count constructions directly (every
other port's own approach) would itself redefine an instance method on
that class, tripping the very world guard being measured and silently
falling back to the slow path before the timed call even ran. The
benchmark harness instead diffs \texttt{GC.stat(:total\_allocated\_}
\texttt{objects)} around each call, needing no redefinition of
anything---safe only because MRI represents \texttt{Float} values as
unboxed flonums, so the only heap allocation in any of these loop
bodies is the tracked \texttt{Data} instance itself.
